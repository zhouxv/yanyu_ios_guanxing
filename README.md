# iosGuanxing 自用桌面版

烟雨江湖存档查看与模拟工具，面向 Windows 桌面使用。当前工程已合并上游 v3.0.9，并加入「自动模拟（自用）」角色洗脉和「弟子洗髓序列（自用）」。

桌面窗口通过 PySide6 / Qt WebEngine 显示本地页面，支持读取存档、模拟操作和导出路线。生成的路线需要在游戏中手动执行。

## 工程功能

| 功能 | 用途 |
| --- | --- |
| 存档管理 | 导入 HAR、保存历史快照，切换历史存档后可下载对应账号的最新云存档 |
| 洗髓模拟 | 按存档状态模拟洗脉、锁脉、置换和序列查询 |
| 自动模拟 | 自动洗脉、自动洗脉（改进）、装备及剑王阁相关预测 |
| 自动模拟（自用） | 七层搜索与置换优化，支持手动设置丹数、导入参考路线和导出结果 |
| 装备模拟 | 打造、升炼、精炼和淬炼，支持橙装图纸和 100 级装备材料，精炼规划可查看最终附加属性合计 |
| 恒山模拟 | 弟子天赋刷新、升级和未来商店推演，上游自动推演可比较未来 3、5、10、30 天候选；自用序列支持批量弟子、三天赋方案、逐日商店及断点续跑 |
| 角色面板与状态 | 查看属性、装备、天赋及培养进度，比较内劲增加 50、100、150 后的作用率，计入精炼、秘技及合斗对内劲和罡气的影响 |
| 鬼市与恒山游货郎 | 根据存档查看货架并推演刷新序列 |

### 恒山弟子洗髓序列（自用）

在桌面观星导入存档，进入 **恒山模拟 → 弟子洗髓序列（自用）**。这个入口在观星内直接运行，无需同时打开外部助手。普通角色的七层洗脉和恒山弟子的单槽洗练是两种不同的模拟。

1. **选弟子。** 可以混选在册、背包和商店候选。商店以存档的游戏日为第 1 天，北京时间 05:00 换日，默认预测 30 天，可设 1～120 天。按天勾选是否手动刷新，再按含首尾的招募日期筛选并选中弟子。今天已手动刷新时只保留存档里的剩余候选。若游戏已换日、存档里的商店仍是昨天的名单，可手动勾选补算一次今日自动刷新，并用游戏中实际名单核对。手动刷新会改变后续天数的名单，未来路线也以游戏中执行同一刷新计划为前提。
2. **选方案。** 默认提供五套常用目标，也可以按分类点选三个天赋，保存为自定义组。可导出当前配置供下次载入；换了存档只复用方案和设置，需重新勾选弟子。同一组三个目标需要同时在身上，槽位顺序与天赋等级不限。批次先跑完第一组的所有弟子，再跑下一组。
3. **搜索。** 每项从原始快照起算；商店弟子先模拟招募，再用招募后的种子和成长属性。从零次洗练逐层搜索至所设上限（默认 4，范围 0～100）。每一步可以推进一天，或刷新任意已开的槽位。允许用其他天赋过渡，也允许暂时洗掉目标；起点或途中出现「刻苦训练」则舍弃。成长至 100 级后仍可用剩余次数洗练。新搜到的路线使用最少洗练次数；同次数不保证最少天数。
4. **看结果和续跑。** 命中后在独立的手动推演页逐步重走，核对每一步的种子、经验和天赋等状态。复验通过才保存，可按招募日期、弟子或方案查找，导出文字、路线图或 JSON。默认每项最多检查 50 万个状态：「预算内无解」表示搜索完成，「达到上限」表示还不能断定无解。暂停后继续保留当前搜索；停止、关页或退出后，回到同一份存档点「继续上次批次」，只从未完成项重新搜索。提高状态上限可以重试原先达到上限的项目。

已完成项与成功路线保存在本机用户数据目录 `hengshan-sequences.sqlite3`，无需保留浏览器缓存。批次断点只对同一份存档生效；已绑定同一账号的不同快照可以共用成功路线。只有内核、弟子起点、招募日期和目标均一致，洗练次数也在预算内，才跳过搜索。无法确定账号时只在当前快照内复用。要沿用外部助手的记录，先设置对应的预测日期与逐日刷新计划，再点「导入旧助手路线文件夹」，选择原来的「成功结果」目录。只导入能与当前名单和起点匹配、且逐步复验通过的路线；不会修改原文件。

### 自用洗脉

入口为「自动模拟 → 自动模拟（自用）」。对照结果里的「原自用」指这个入口升级前的七层版本，当前入口运行新自用。

#### 新自用的整体思路

新自用从角色当前的天赋、槽位和脉序出发，比较**凑齐整套目标一共花多少洗髓丹**。路线结束时，全部必选脉要同时在场，每个兼容组至少留一条。前段多花几丹垫洗，如果能让后段少锁一条脉洗上百次，整条路线就可能更省。

1. **先用七层找路。** 有参考路线就先回放，达标且在预算内便记为候选。随后在允许的槽数和耗丹上限内，逐层比较先拿哪条目标脉、提前锁哪条同类低阶脉、何时开槽。每层可以连续洗很多次，再把不同的局面交给下一层，每轮最多七层。
2. **再从同一起点补查三类走法。** 一是改变首次置换前的垫洗次数，挑后续目标出现较早的脉序。二是尝试把必选紫脉免费换回同名，留住目标并推进置换顺序。三是把开第四槽的时机和连续置换放在一起比较，必要时先留一条非目标紫脉，等其他目标到齐再换掉它。七层尚无路线时，这些分支仍可在设定的丹数上限内独立找路。
3. **只用回放通过的更省路线更新结果。** 一旦有了达标路线，后续搜索的上限就降到比它少一丹。程序从存档起点重走候选路线，核对置换结果、最终槽位和累计耗丹。各阶段按搜索深度、候选数量和固定工作量收尾，最终给出本次找到的最低丹耗，或显示预算内未找到路线。

#### 使用方法

1. 导入存档，选择人物、VIP、允许开启的槽数、保留天赋和目标紫脉。
2. 设置「可用洗髓丹」和「最大耗丹数量」。
3. 点击「开始七层搜索」。界面显示当前阶段和已经找到的最低丹耗。
4. 查看逐步操作，按需导出路线。搜索期间可以暂停、继续，也可以停止并导出已找到的路线。

「可用洗髓丹」默认读取背包，可手动修改或恢复存档丹数。当背包丹数大于零且低于搜索上限时，七层策略先按背包丹数找一轮。「最大耗丹数量」决定一条路线允许花多少丹。结果会列出按当前背包走完还剩多少丹或缺多少丹。切换人物会保留手动丹数，重新导入存档后读取新存档丹数。修改搜索条件后需要重新搜索。

也可载入 TXT 或 Markdown 参考路线。程序先从当前存档回放，达标且在预算内的路线会成为已有候选，后续仍从当前存档起步。

#### 改进、原自用和新自用有什么区别

两个版本共用洗脉、开槽和置换规则，都以凑齐整套目标的总丹耗衡量路线。表中的七层搜索来自原自用，新自用在七层之后又吸收了上游的三类走法。

| 决策 | 上游「自动洗脉(改进)」 | 新「自动模拟（自用）」 |
| --- | --- | --- |
| 第四紫可以十选一时，先搜谁？ | 先拆成十套具体的四紫目标，每套从同一角色起点找路。 | 七层搜索让十个选项共用前段。实际洗出组内紫脉，再决定留哪条，后续专门搜索才拆成具体组合。 |
| 怎样找到置换机会？ | 构造路线时，遇到低阶脉就预看接下来几洗，若同类紫脉将出现，就尝试提前锁住低阶脉。 | 七层看到天然紫脉，还会回看前面出现过的同类低阶脉，重走提前锁脉的分支，比较当场置换与多垫几洗的总花费。 |
| 搜到哪里停？ | 四个阶段逐步提高强度，把时间分给各组和各种方法。三紫、四紫默认总时限为 15 分钟。 | 每轮最多七层，一层可连续洗很多次。每层把不同锁法、置换顺序的局面留给下一层。后续各项搜索也有各自的候选或工作量上限。 |
| 已经找到一条路线，还查什么？ | 利用剩余时间扩大置换脉序范围，比较更多锁法和开槽时机。保留多条候选，先按耗丹、再按洗数排序。 | 带着当前最低丹耗，从原存档分别试首次置换前垫洗、必选脉换回同名、开槽配合连续置换。最后一项若有多个入选组合，会给当前最低丹路线的目标组合额外预留一半检查次数。 |

#### 七层之后怎样继续省丹

1. **比较首次置换前垫几洗。** 先留住能触发置换的同类低阶脉和可置换的紫脉。欧气尚未固定时，最多向后试探 200 次垫洗，预看不同停点的后续紫脉。优先完整模拟目标出现得多、出现得早的走法。若第四紫来自兼容组，也可以把已经合格的一条换成同组另一条。
2. **比较必选紫脉换回同名。** 当必选紫脉自然出现、欧气尚未固定，先检查它能否免费换回自己。这一步既能留下目标，又能推进置换顺序。随后再比较暂留哪条非目标紫脉、何时开第四槽，直到最终目标凑齐。
3. **把开槽时机和连续置换一起比较。** 对三紫、四紫目标，调用上游的战术搜索，比较起手开第四槽、先拿到冲突紫脉再开槽等走法。途中可以留一条非目标紫脉，等其他目标出现后连续免费置换收尾。若有多个入选的目标组合，会给当前最低丹路线的组合更多检查机会。

每个分支都比较**整条路线的总丹耗**。例如已有 4,006 丹的路线，后续分支的上限就降到 4,005 丹。新路线从存档起点逐步回放，核对置换结果、最终槽位和总丹耗后才会替换当前结果。「未找到」表示本次搜索在设定预算内没有返回达标路线。搜索顺序可查阅[上游改进入口](web/shared/auto_wash2_worker.js)和[自用入口](web/shared/personal_wash_worker.js)。

v3.0.9 的战术搜索在洗出新目标时，会比较继续锁住原先的低阶冲突脉和放开它两种走法。上游给一份特定的步惊云存档附带了参考路线。自用会标明这种提前返回的路线，回放通过后保留，再用剩余检查次数从同一起点寻找更低丹耗。两个入口都等人物脉池读完才可点选「金顶混」，条件不足时会列出缺少的紫脉和所需条件。

#### 三槽起步、5,000 丹的对照结果

以下数据来自 v3.0.8 的对照。同一份存档中 14 名未洗脉角色各测两组，均允许开第四槽。金顶混三紫要求转世金仙、岿然顶天、混元奇脉。四紫再从 10 条兼容紫脉中任选一条。下表是新自用相对原自用省丹的全部五组，数字均为回放通过的洗髓丹用量。

| 角色与目标 | 上游改进 | 原自用 | 新自用 | 新路线怎么走 |
| --- | ---: | ---: | ---: | --- |
| 石小鲁 · 四紫 | 3,473 | 4,006 | 3,473 | 在三槽锁住枪棍高手和枪棍绝伦，垫 14 洗，换成同组的不灭肉身再开第四槽。 |
| 沙孤兰 · 三紫 | 3,284 | 3,499 | 3,284 | 首次置换前垫 101 洗，拿到转世金仙后才在累计 1,828 丹时开第四槽。 |
| 白鹭 · 三紫 | 4,804 | 4,909 | 4,704 | 拿到转世金仙后，在累计 880 丹时开第四槽，1,000 丹时把转世金仙换回同名，后段保留九阴鬼脉再换岿然顶天。 |
| 南宫靖一 · 三紫 | 1,576 | 1,610 | 1,576 | 在三槽锁刀法高手再洗两次，拿到刀法绝伦才开第四槽，全程做了六次免费置换。 |
| 孟翔 · 三紫 | 4,211 | 4,168 | 3,560 | 起手就开第四槽，先收转世金仙，留九阴鬼脉等混元奇脉出现，最后用两次免费置换拿到岿然顶天。 |

石小鲁多垫的 14 洗花了 84 丹，后面三锁洗脉的开销从原自用的 2,070 丹降到 1,220 丹。白鹭的两条路线都把转世金仙换回同名。上游先在三槽垫 30 洗，再置换，累计 1,092 丹才开第四槽。新自用在 880 丹开第四槽，垫 15 洗就置换。两条路线最后都锁转世金仙和九阴鬼脉洗 451 次，各花 3,608 丹。新自用省下的 100 丹全部在这段双锁之前。

28 组里，上游找到 11 组，新自用在其中 6 组更省、5 组持平。两代自用各找到 14 组，其中新自用 5 组更省、9 组持平。比上游多找到的三组在原自用里已有路线，分别是陈元封四紫、姜逸尘四紫和拓拔浚三紫。其余 14 组在本次预算内均未找到。

## 支持范围与版本限制

| 项目 | 当前范围 |
| --- | --- |
| 桌面系统 | Windows 10 / 11，x64 |
| 工程版本 | 当前基于上游 v3.0.9，版本定义位于 `desktop/__init__.py` |
| 源码环境 | Windows 版 Python 3.11，64 位；项目使用独立 `.venv` |
| 自用与改进自动洗脉界面 | 当前支持国服、先行服；界面会拒绝国际服存档 |
| 自用洗脉资质 | 150–154，在所选开槽范围内比较当前槽数和逐步开槽的走法 |
| 目标与预算 | 最多四槽目标，可设置必选脉和兼容组；最大耗丹数量为 0–20,000 的整数 |
| 国际服 | HAR 导入包含国际服处理及完整存档回退；手动洗髓模拟保留国际服算法入口，具体数据需要对应渠道适配 |
| 游戏存档版本 | 解析依赖存档格式、内置密钥表和渠道；模拟依赖当前算法及数据表。游戏更新后需重新核对适配情况 |

工程版本号与游戏的 `DBVersion` 是不同信息。现有代码没有统一的游戏版本号白名单；存档成功导入后，仍应核对渠道、人物、天赋、丹数和实际操作结果。

自用搜索只计算洗髓丹，开槽所需资质等条件需要在游戏中满足。界面修改的丹数和模拟操作作用于本次推演。

## 环境设置与依赖安装

在项目根目录打开终端，选择对应的一组命令执行。

先安装 Windows 版 64 位 Python 3.11 和 Python 启动器 `py`，用 `py -3.11 --version` 确认可用。依赖清单 `requirements-desktop.txt` 统一包含 PySide6、xxtea 和 PyInstaller，安装后即可启动和打包。

| 依赖 | 清单中的版本约束 |
| --- | --- |
| PySide6 | Windows 固定为 6.10.2 |
| xxtea | 6.0 ≤ 版本 < 7 |
| PyInstaller | 6.10 ≤ 版本 < 7 |

### Git Bash / UCRT64

```bash
py -3.11 -m venv .venv &&
./.venv/Scripts/python.exe -m pip install -r requirements-desktop.txt &&
./.venv/Scripts/python.exe -m pip check &&
./.venv/Scripts/python.exe desktop_main.py
```

### PowerShell

逐行执行，每一步成功后再继续。

```powershell
py -3.11 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-desktop.txt
.\.venv\Scripts\python.exe -m pip check
.\.venv\Scripts\python.exe desktop_main.py
```

以上命令直接使用项目虚拟环境中的 Python。以后可双击 `启动观星.cmd`。拉取代码后，如果依赖清单更新，重新运行对应终端的安装依赖命令。

遇到 `No module named 'PySide6'`、`No module named 'xxtea'` 或 `No module named 'PyInstaller'`，在同一个 `.venv` 中重新安装依赖，确认成功后再启动或打包。

Node.js 22 或更高版本用于 JavaScript 测试和洗脉性能对比。日常运行及本机 EXE 打包使用 Python 环境。

## 导入存档与日常使用

1. 双击 `启动观星.cmd`，或运行已打包的 `iosGuanxing.exe`。
2. 选择或拖入 HAR 文件。程序优先从 HAR 读取会话，向游戏服务器请求当前云存档。
3. 若下载失败，程序会尝试从 HAR 中读取完整存档，并显示实际使用的数据来源。HAR 只有部分响应或会话信息时，需要重新抓取。
4. 导入成功后进入各模拟页面；后续可用「下载最新云存档」刷新，或打开历史快照。

首页另有文件导入入口。通过首页导入的数据供本次网页模拟使用；原生历史快照由桌面的 HAR 导入和云存档下载流程保存。

获取 HAR 时，用 ProxyPin 等抓包工具记录游戏的登录及下载存档请求，再导出 HAR。云存档刷新依赖可用的网络和会话。存档加载后，各模拟功能在本机执行。

## 打包为单文件 EXE

安装依赖后双击 `打包观星.cmd`，或在终端执行。

Git Bash / UCRT64：

```bash
./.venv/Scripts/python.exe -m pip install -r requirements-desktop.txt &&
./打包观星.cmd
```

PowerShell：

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-desktop.txt
.\打包观星.cmd
```

生成文件位于 `dist/iosGuanxing.exe`，可以单独复制运行。修改源码后需要重新打包，已有 EXE 才会包含新改动。打包脚本会检查 Python 和 PyInstaller，并限定打包时的 DLL 搜索目录。

## 本地数据与设置

- 历史存档、桌面偏好和诊断日志保存在 `%LOCALAPPDATA%\iosGuanxing`。
- Windows 会话凭据使用当前用户的 DPAPI 加密；历史存档快照以明文 JSON 保存。
- 搜索中的暂停状态限当前页面使用。关闭窗口会结束后台搜索。
- `启动观星.cmd` 设置 `IOSGUANXING_DISABLE_AUTO_UPDATE=1`，关闭启动时的自动更新检查。

桌面「检查更新」当前查询的是上游发布版本。获取包含自用功能的更新时，应拉取本仓库代码并重新打包。

## 工程结构与维护

| 路径 | 用途 |
| --- | --- |
| `desktop_main.py`、`desktop/` | 原生窗口、本机页面服务、存档管理和更新检查 |
| `web/` | 桌面内嵌页面、算法、数据表及 WASM 资源 |
| `web/shared/personal_wash*` | 自用洗脉界面和搜索实现 |
| `yyjh/`、`keys.json` | 桌面使用的 HAR、协议、解密和存档处理 |
| `assets/`、`iosGuanxing.spec` | 图标和单文件打包配置 |
| `tests/`、`dev/` | 回归测试、桌面检查及开发工具 |
| `.github/workflows/` | 自动测试与 Windows 构建发布 |

同步上游时，先合并上游正式标签并保持「自动洗脉（改进）」与上游一致，再评估是否将相关修复适配到自用模块。上游合并和自用适配分别提交。

本分支已移除旧命令行工具、ADB 内存扫描、解包与逆向工具、独立网页服务器及 Gitee 发布脚本。同步上游遇到这些文件的修改／删除冲突时，应按桌面功能的实际依赖处理。`web/homestead/` 家园模块暂时保留，当前桌面导航没有入口。
